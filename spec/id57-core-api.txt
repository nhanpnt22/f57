============================================================
ABSTRACT
============================================================

ID57 Core API defines a minimal, canonical interface for
generating human-centric identifiers using a one-way
transformation pipeline based on cryptographic hashing,
controlled prefix truncation, and B57 encoding.

It standardizes deterministic, ASCII-safe, compact
identifier generation while ensuring canonical form and
entropy-derived security properties.

ID57 is strictly an identifier profile and MUST NOT be used
for reversible encoding.

============================================================
STATUS OF THIS MEMO
============================================================

This document is provided for informational purposes.

This memo is intended for production use.

============================================================
1. INTRODUCTION
============================================================

ID57 Core API defines the minimal function set required to
produce canonical, bounded-length identifiers.

ID57 is a one-way transformation:

 input → HASH → truncate → B57 → identifier

Goals:

- deterministic output
- canonical representation
- compact identifiers
- human readability
- controlled entropy reduction
- minimal API surface

ID57 MUST NOT introduce reversibility, ambiguity, or
post-encoding transformations.

2. CONVENTIONS AND TERMINOLOGY
============================================================

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL",
"SHALL NOT", "SHOULD", "SHOULD NOT", and "MAY" are to be

============================================================
3. DEPENDENCIES
============================================================

ID57 Core API depends on:

- B57 Core API
- Cryptographic hash functions

Requirements:

- B57 encoding MUST remain canonical and bijective
- Hash functions MUST be cryptographic
- BLAKE3 SHOULD be the primary default hash function
- ID57 MUST NOT redefine or modify B57 behavior

============================================================
4. CORE DEFINITION
============================================================

Given:

 input_bytes

Compute:

 hash_bytes = HASH(input_bytes)
 truncated_bytes = truncate_bytes(hash_bytes, bits(L))
 id57 = b57_encode(truncated_bytes)

Where:

- HASH is a cryptographic hash function
- L is a predefined length_enum mapped to bit length
- Truncation MUST occur at byte level using prefix truncation
- Encoding MUST be canonical B57

============================================================
5. CORE FUNCTION
============================================================

5.1 id57_generate

function id57_generate(input_bytes, length_enum) -> string

Optional extension:

function id57_generate(input_bytes, hash_fn, length_enum) -> string

Binding compatibility note:

- Some language bindings require the hash_fn argument and treat
  BLAKE3 as the effective default when unspecified by caller.

Definition:

 hash_bytes = HASH(input_bytes)

 if length_enum == ID57_DEFAULT:
     effective_bytes = truncate_bytes(hash_bytes, bits(ID57_LEN_128))
 else:
     effective_bytes = truncate_bytes(hash_bytes, bits(length_enum))

 output = b57_encode(effective_bytes)

Requirements:

- HASH MUST be cryptographic
- HASH MUST be deterministic
- BLAKE3 SHOULD be the primary default
- If hash_fn is exposed, it MUST be cryptographic and deterministic
- Truncation MUST be prefix-based
- Truncation MUST occur BEFORE encoding
- Encoding MUST be canonical B57
- Output MUST be deterministic
- Input MUST NOT be modified

- length_enum MUST be one of defined ID57 values or DEFAULT

------------------------------------------------------------

5.2 id57_generate_fixed4

function id57_generate_fixed4(input_bytes) -> string

Optional extension:

function id57_generate_fixed4(input_bytes, hash_fn) -> string

This is the sole fixed-width ID57 output (7.2.1): always
exactly 4 characters, never a range. It intentionally departs
from the standard pipeline (5.1) in two ways: it reduces the
truncated value modulo 57^4 before encoding, and it zero-pads
the result to a fixed width. Both are prohibited for every
other ID57 length_enum (8 TRUNCATION MODEL, 14 PROHIBITED
BEHAVIORS) and MUST NOT be applied there; they are permitted
here only because this function is explicitly, separately
specified and never defines a decoding interface (9).

Definition:

 hash_bytes = HASH(input_bytes)

 truncated_bytes = truncate_bytes(hash_bytes, 32)
                    // same 32-bit/4-byte truncation as ID57_LEN_32

 value = bytes_to_uint_be(truncated_bytes)   // 0 .. 2^32-1

 reduced = value mod 57^4                     // 0 .. 57^4-1 (10,556,001 buckets)

 digits = to_base57_digits(reduced)           // minimal digits, no leading zero digit
 output = ALPHABET[0] * (4 - length(digits)) + digits
                    // left-pad with the zero-value alphabet character to width 4

 return output   // length(output) == 4, always

Requirements:

- HASH MUST be cryptographic and deterministic
- truncated_bytes MUST be derived via prefix truncation, as in 8
- the modulo reduction MUST use the full 32-bit truncated value
  (not a bit-level pre-truncation to fewer bits)
- output MUST always be exactly 4 characters
- output MUST use only B57 alphabet characters

Security / entropy notes:

- Effective output space is 57^4 (~23.33 bits), smaller than
  the 32-bit truncation it is derived from; ~8.7 bits are
  discarded by the modulo reduction
- 2^32 is not an exact multiple of 57^4, so the reduction has
  a small modulo bias (some outputs are marginally more likely
  than others); this is acceptable for a non-security,
  informational identifier but MUST NOT be used where unbiased
  output is required
- Collision guidance for this function follows the ~23-bit row
  in 10.1 (~2^11-2^12 entries), same as ID57_LEN_24

============================================================
6. DEFAULT BEHAVIOR
============================================================

ID57_DEFAULT:

- MUST resolve to ID57_LEN_128
- MUST produce identifiers of at most 22 characters
  (16-22 chars; see 7.3 for the length bounds model)
- MUST NOT preserve full hash entropy

Default pipeline:

 id57 = b57_encode(truncate_bytes(HASH(input), 128-bit))

============================================================
7. LENGTH MODEL
============================================================

Implementations MUST support:

Character length is a BOUND, NOT a guarantee. B57 is a
bignum-style positional encoding: the exact number of
characters produced for a given length_enum depends on the
numeric value of the truncated hash, and MAY be shorter than
the maximum shown below. Implementations MUST NOT generate,
reject, or validate an identifier by requiring an exact
character count. See 7.3 for the normative bounds formula
and 11.4/11.5 for the required range/validation functions.

------------------------------------------------------------
7.1 Security Lengths (REQUIRED)
------------------------------------------------------------

- ID57_LEN_8   → 1-2 chars
- ID57_LEN_16  → 2-3 chars
- ID57_LEN_32  → 4-6 chars
- ID57_LEN_64  → 8-11 chars
- ID57_LEN_128 → 16-22 chars (DEFAULT)
- ID57_LEN_256 → 32-44 chars
- ID57_LEN_512 → 64-88 chars

------------------------------------------------------------
7.2 Informational Lengths (NON-SECURITY)
------------------------------------------------------------

- ID57_LEN_24  → 3-5 chars
- ID57_LEN_48  → 6-9 chars
- ID57_LEN_96  → 12-17 chars
- ID57_LEN_192 → 24-33 chars
- ID57_LEN_384 → 48-66 chars

All five are byte-aligned (3/6/12/24/48 bytes) and form a
doubling sequence. None of them share a byte_length with any
7.1 security length (1/2/4/8/16/32/64 bytes), so - unlike the
prior informational set - no informational length_enum's
range or decoded shape can be confused with a security one.

------------------------------------------------------------
7.2.1 Fixed-Width Special Case: id57_generate_fixed4
------------------------------------------------------------

One additional, explicitly special-cased identifier exists
outside the length_enum model above: id57_generate_fixed4
(5.2). It is the only ID57 output that is a truly fixed
4 characters, always - not a [min_chars, max_chars] bound.

This is NOT achievable by picking a smaller length_enum and
applying 7.3's normal formula: max_chars computed from any
whole byte_length never lands on exactly 4 (2 bytes -> max 3,
3 bytes -> max 5; 4 is unreachable). Achieving an exact 4
requires a different mechanism - see 5.2 for the algorithm
(modulo reduction into 57^4 plus fixed-width zero-padding).
id57_generate_fixed4 MUST NOT be confused with, or treated as
interchangeable with, ID57_LEN_24 (3-5 chars) - they have
different algorithms and different entropy properties.

------------------------------------------------------------
7.3 Length Bounds (NORMATIVE)
------------------------------------------------------------

For any length_enum, with bit_length = bits(length_enum):

 byte_length = ceil(bit_length / 8)
 min_chars   = byte_length
 max_chars   = b57_encoded_length(byte_length)
             = ceil(byte_length * 8 / log2(57))

The ranges in 7.1 and 7.2 are derived directly from this
formula and MUST be treated as [min_chars, max_chars]
bounds, never as a fixed width. This formula does NOT apply
to id57_generate_fixed4 (7.2.1, 5.2), which is exactly 4
chars by construction, not by this bound.

Requirements:

- Length MUST correspond to defined model values
- Implementations MUST NOT accept arbitrary lengths
- Security-sensitive use MUST use ≥ ID57_LEN_128
- Implementations MUST NOT assume or enforce a fixed
  character count for any length_enum (id57_generate_fixed4
  is the sole, explicitly-documented exception)

============================================================
8. TRUNCATION MODEL
============================================================

Definition:

 truncate_bytes(hash_bytes, bit_length)

Rules:

- MUST operate on raw hash bytes
- MUST occur BEFORE B57 encoding
- MUST use prefix truncation
- MUST be deterministic

Bit handling:

- bit_length MUST be converted to byte length using:
  byte_length = ceil(bit_length / 8)
- Excess bits in the final byte MUST be truncated (not rounded)

Prohibited:

- truncating encoded strings
- suffix truncation
- post-encoding manipulation

============================================================
9. ONE-WAY PROPERTY
============================================================

ID57 is a one-way transformation:

- Original input is computationally infeasible to recover
- ID57 does not define a decoding interface
- Any decoding yields truncated hash bytes only,
  which have no reversible relation to original input

Security depends on hash function properties.

============================================================
10. SHORT-LENGTH USAGE (ID57_LEN_24/48/96/192/384, id57_generate_fixed4)
============================================================

This section applies specifically to identifiers generated
with the informational lengths defined in 7.2 (ID57_LEN_24,
ID57_LEN_48, ID57_LEN_96, ID57_LEN_192, ID57_LEN_384) and to
id57_generate_fixed4 (5.2, 7.2.1). These trade collision
resistance for compactness and carry additional usage
requirements beyond the general ID57 rules. ID57_LEN_32 (from
7.1) is also commonly used at this end of the range and is
included in the guidance below where relevant.

There is no separate "short" profile, module, or API. Short
identifiers are produced by calling id57_generate (5.1) with
one of these length_enum values directly - e.g.
id57_generate(x, ID57_LEN_48) for a 6-9 char short identifier,
or id57_generate_fixed4(x) for a hard-fixed 4-char identifier.
Implementations MUST NOT expose a distinct short-specific
function name, type, or default beyond id57_generate_fixed4
itself (this consolidates what a prior ID57-SHORT companion
profile specified separately; see 17 REVISION NOTES).

------------------------------------------------------------
10.1 Collision Model
------------------------------------------------------------

Approximate collision onset (birthday bound):

- id57_generate_fixed4 (~23.33-bit effective space) → ~2^11-2^12 entries
- ID57_LEN_24 (24-bit) → ~2^12 entries
- ID57_LEN_32 (32-bit, from 7.1) → ~2^16 entries
- ID57_LEN_48 (48-bit) → ~2^24 entries
- ID57_LEN_96 (96-bit) → ~2^48 entries
- ID57_LEN_192 (192-bit) → ~2^96 entries
- ID57_LEN_384 (384-bit) → ~2^192 entries

------------------------------------------------------------
10.2 Required Safety Mechanisms
------------------------------------------------------------

Implementations MUST:

- detect collisions before insertion
- reject or regenerate on collision
- scope identifiers within a namespace

Implementations MUST NOT:

- assume uniqueness
- use identifiers without verification

------------------------------------------------------------
10.3 Recommended Patterns
------------------------------------------------------------

Dual-Identifier Model:

 short_id = id57_generate(x, ID57_LEN_48)
 full_id  = id57_generate(x, ID57_LEN_128)

Namespaced Identifiers:

 short_id = id57_generate(namespace || x, L)

Collision-Aware Allocation:

 loop:
   id = id57_generate(x || counter, L)
   if not exists(id):
     store(id)
     break

Progressive Length Upgrade:

 id57_generate_fixed4 → ID57_LEN_24 → ID57_LEN_32 →
 ID57_LEN_48 → ID57_LEN_96 → ID57_LEN_192 → ID57_LEN_384

------------------------------------------------------------
10.4 Use Cases
------------------------------------------------------------

Suitable for:

- short URLs
- QR code payload minimization
- user IDs (non-sensitive)
- invite codes
- temporary tokens
- UI-friendly identifiers

------------------------------------------------------------
10.5 Prohibited Usage
------------------------------------------------------------

MUST NOT be used for:

- authentication tokens
- authorization systems
- cryptographic identity
- globally unique identifiers
- security-critical systems

11. OPTIONAL FUNCTIONS
============================================================

11.1 id57_verify

function id57_verify(input_bytes, id57_string, length_enum) -> boolean

Optional extension:

function id57_verify(input_bytes, hash_fn, id57_string, length_enum) -> boolean

 expected = id57_generate(input_bytes, length_enum)

 return (expected == id57_string)

------------------------------------------------------------

11.2 id57_is_valid

function id57_is_valid(id57_string) -> boolean

- MUST validate characters using B57 rules
- MUST reject INVALID_CHAR

------------------------------------------------------------

11.3 id57_is_canonical

function id57_is_canonical(id57_string) -> boolean

 decoded = b57_decode(id57_string)
 reencoded = b57_encode(decoded)

 return (id57_string == reencoded)

------------------------------------------------------------

11.4 id57_range

function id57_range(length_enum) -> (min_chars, max_chars)

 bit_length  = bits(length_enum)
 byte_length = ceil(bit_length / 8)

 return (
   byte_length,
   b57_encoded_length(byte_length)
 )

------------------------------------------------------------

11.5 id57_is_length

function id57_is_length(id57_string, length_enum) -> boolean

 (min_chars, max_chars) = id57_range(length_enum)

 if length(id57_string) < min_chars or
    length(id57_string) > max_chars:
       return false

 if not id57_is_canonical(id57_string):
       return false

 decoded     = b57_decode(id57_string)
 bit_length  = bits(length_enum)
 byte_length = ceil(bit_length / 8)

 if length(decoded) != byte_length:
       return false

 excess_bits = byte_length * 8 - bit_length
 if excess_bits > 0:
     last_byte = decoded[byte_length - 1]
     if (last_byte & ((1 << excess_bits) - 1)) != 0:
         return false

 return true

Requirements:

- MUST be used instead of exact character-count comparison
  for any length conformance check
- MUST NOT be used to infer length_enum from an unknown
  string; distinct length_enum values MAY share the same
  byte_length and therefore the same valid range and the
  same decoded shape (see 7.3 note)

============================================================
12. INVARIANTS
============================================================

The following MUST hold:

 id57_generate(x, L) ==
 b57_encode(truncate_bytes(HASH(x), bits(L)))

Determinism:

 same input + same configured hash + same length -> same output

Canonical constraint:

 b57_encode(b57_decode(y)) == y
 (only if y is canonical)

============================================================
13. ERROR MODEL
============================================================

Implementations MUST distinguish:

- INVALID_CHAR
- NON_CANONICAL
- INVALID_LENGTH_ENUM

Requirements:

- Errors MUST be deterministic
- MUST NOT continue after failure
- MUST NOT use ambiguous errors

============================================================
14. PROHIBITED BEHAVIORS
============================================================

Implementations MUST NOT:

- bypass hashing stage
- encode raw input directly
- truncate after encoding
- use suffix truncation
- accept arbitrary lengths
- normalize or transform identifiers
- re-hash encoded values
- introduce randomness

============================================================
15. SECURITY CONSIDERATIONS
============================================================

ID57 provides no cryptographic guarantees beyond the
underlying hash function.

Security depends on:

- hash function strength (BLAKE3 recommended)
- truncation length
- entropy preservation

Shorter identifiers reduce security proportionally.

Encoded length MUST NOT be treated as a guarantee.

17. REVISION NOTES
============================================================

v0.1.1:

- Corrected the length model (7.1/7.2): character counts for
  non-byte-aligned lengths (23, 29, 47, 70, 93, 186, 373 bits)
  were undercounted by 1 char versus their true maximum, and
  all lengths were incorrectly presented as fixed rather than
  bounded. Replaced with normative [min_chars, max_chars]
  ranges (7.3).
- Added id57_range and id57_is_length (11.4, 11.5) as the
  required mechanism for length conformance checks. Exact
  character-count comparison MUST NOT be used.
- No change to id57_generate, truncation, or B57 behavior;
  this is a documentation and validation-API correction only.

v0.2.0:

- Merged the ID57-SHORT PROFILE companion document into this
  spec (new section 10: SHORT-LENGTH USAGE). There is no
  longer a separate profile, module, or API for short
  identifiers - id57_generate/id57_verify/id57_range/
  id57_is_length already cover ID57_LEN_23/29/32/47/70
  directly. id57-short-profile.txt is now a deprecation
  pointer to this document.
- BREAKING for implementations: the id57s_generate,
  id57s_range, id57s_is_length function names and any
  ID57-SHORT-specific default/type (e.g. ID57ShortLength,
  ID57S_DEFAULT) MUST be removed. Callers needing a short
  identifier call id57_generate(x, ID57_LEN_47) (or another
  short length_enum) directly.
- Collision model, required safety mechanisms, recommended
  patterns, use cases, and prohibited usage for short lengths
  moved to 10.1-10.5 verbatim in substance.

v0.3.0:

- BREAKING: replaced the entire informational length set
  (7.2). ID57_LEN_23, ID57_LEN_29, ID57_LEN_47, ID57_LEN_70,
  ID57_LEN_93, ID57_LEN_186, ID57_LEN_373 are REMOVED and
  replaced by ID57_LEN_24, ID57_LEN_48, ID57_LEN_96,
  ID57_LEN_192, ID57_LEN_384 - a byte-aligned doubling
  sequence with no byte_length overlap with any 7.1 security
  length (the prior set had one: ID57_LEN_29/ID57_LEN_32
  shared byte_length 4).
- Added id57_generate_fixed4 (5.2) - the one ID57 output that
  is a genuinely fixed 4 characters, always. Unlike every
  other length, it uses modulo reduction (value mod 57^4) and
  fixed-width zero-padding rather than the standard
  truncate-then-encode pipeline; see 7.2.1 for why no
  length_enum/7.3 combination can reach exactly 4 chars, and
  5.2 for the algorithm and its entropy/bias trade-offs.
- Updated 10 (SHORT-LENGTH USAGE), including 10.1 collision
  model and the 10.3 progressive-length-upgrade pattern, for
  the new length set and id57_generate_fixed4.
- No change to id57_generate's algorithm for existing lengths,
  to B57, or to the security length set (7.1).
