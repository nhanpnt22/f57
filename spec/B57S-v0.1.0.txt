============================================================
ABSTRACT
============================================================

B57S defines a unified, layered system for binary encoding,
hash representation, and identifier generation based on:

- B57 (encoding layer)
- H57 (hash representation layer)
- ID57 (identifier profile)

It standardizes deterministic, ASCII-safe, canonical, and
entropy-consistent transformations from raw input data to
human-readable outputs.

============================================================
1. INTRODUCTION
============================================================

B57S defines a composable transformation stack:

 input → HASH → truncate → B57 → string

Layer separation:

- B57  → encoding primitive
- H57  → full hash representation
- ID57 → truncated identifier profile

Goals:

- deterministic behavior
- canonical representation
- entropy preservation (B57, H57)
- controlled entropy reduction (ID57)
- minimal and consistent API design

============================================================
3. ARCHITECTURE OVERVIEW
============================================================

------------------------------------------------------------
3.1 B57 (Encoding Layer)
------------------------------------------------------------

 bytes ↔ B57 string

Properties:

- bijective
- deterministic
- entropy-preserving
- canonical

------------------------------------------------------------
3.2 H57 (Hash Representation Layer)
------------------------------------------------------------

 input → HASH → bytes → B57 → string

Definition:

 H57(x) = b57_encode(HASH(x))

Properties:

- full entropy preservation
- canonical representation
- no truncation

------------------------------------------------------------
3.3 ID57 (Identifier Profile)
------------------------------------------------------------

 input → HASH → truncate → B57 → string

Definition:

 ID57(x, L) = b57_encode(truncate_bytes(HASH(x), bits(L)))

Properties:

- controlled entropy reduction
- fixed-length identifiers
- one-way transformation

------------------------------------------------------------
3.4 Relationship
------------------------------------------------------------

- B57 is the foundation
- H57 builds on B57
- ID57 builds on H57

Constraint:

 ID57 ⊂ H57

============================================================
4. CORE TRANSFORMATIONS
============================================================

4.1 Encoding:

 b57_encode(bytes) → string
 b57_decode(string) → bytes

4.2 Hash Representation (H57):

 h57 = b57_encode(HASH(input_bytes))

4.3 Identifier Generation (ID57):

 hash_bytes      = HASH(input_bytes)
 effective_bytes = truncate_bytes(hash_bytes, bits(L))
 id57            = b57_encode(effective_bytes)

============================================================
5. HASH FUNCTION MODEL
============================================================

Hash functions:

- MUST be cryptographic
- MUST be deterministic
- MUST produce fixed-length output
- MUST provide uniform distribution

Recommended:

- BLAKE3 (primary)
- SHA-256
- SHA-512

Constraints:

- MUST NOT use non-cryptographic hashes
- MUST NOT infer hash function from output

============================================================
6. TRUNCATION MODEL
============================================================

Definition:

 truncate_bytes(hash_bytes, bit_length)

Rules:

- MUST operate on raw bytes
- MUST occur BEFORE B57 encoding
- MUST use prefix truncation
- MUST preserve big-endian ordering
- MUST be deterministic

Bit handling:

 byte_length = ceil(bit_length / 8)

- Excess bits in final byte MUST be truncated

Prohibited:

- truncating encoded strings
- suffix truncation
- post-encoding manipulation

============================================================
7. LENGTH MODEL
============================================================

7.1 Canonical Full-Length (H57):

- 256-bit → 44 chars
- 512-bit → 88 chars

7.2 ID57 Default:

- ID57_DEFAULT = ID57_LEN_128
- bits(ID57_LEN_128) = 128
- output length = 22 chars

7.3 Security Thresholds:

- 2 chars → ≥ 8-bit
- 3 chars → ≥ 16-bit
- 6 chars → ≥ 32-bit
- 11 chars → ≥ 64-bit
- 22 chars → ≥ 128-bit (minimum)
- 44 chars → ≥ 256-bit
- 88 chars → ≥ 512-bit

Constraints:

- MUST use predefined length enums
- MUST NOT accept arbitrary lengths
- Security-sensitive use MUST use ≥ 128-bit

============================================================
8. DETERMINISM AND CANONICAL FORM
============================================================

All layers MUST be deterministic:

 same input → same output

Canonical constraints:

- B57 outputs MUST be canonical
- No normalization or transformation allowed
- Exactly one valid representation per input

============================================================
9. INVARIANTS
============================================================

B57:

 b57_decode(b57_encode(x)) == x

H57:

 H57(x) == b57_encode(HASH(x))

ID57:

 ID57(x, L) ==
 b57_encode(truncate_bytes(HASH(x), bits(L)))

Canonical constraint:

 b57_encode(b57_decode(y)) == y
 (only if y is canonical)

============================================================
10. ERROR MODEL
============================================================

Implementations MUST distinguish:

- INVALID_CHAR
- NON_CANONICAL
- INVALID_LENGTH_ENUM
- ENTROPY_EXCEEDED

Requirements:

- MUST fail deterministically
- MUST NOT continue after error
- MUST NOT use ambiguous errors

============================================================
11. PROHIBITED BEHAVIORS
============================================================

Implementations MUST NOT:

- modify B57 alphabet
- use non-cryptographic hashes
- bypass hashing in ID57/H57
- truncate after encoding
- use suffix truncation
- accept arbitrary lengths
- normalize or transform outputs
- re-hash encoded values
- introduce randomness
- produce non-canonical outputs

============================================================
12. SECURITY CONSIDERATIONS
============================================================

B57S provides no cryptographic guarantees beyond the
underlying hash function.

Security depends on:

- hash function strength (BLAKE3 recommended)
- entropy preservation (H57)
- truncation length (ID57)

Notes:

- H57 preserves full entropy
- ID57 reduces entropy intentionally
- Shorter outputs reduce security proportionally

Encoded length MUST NOT be treated as a guarantee.

15. USE CASES
============================================================

B57S defines a composable transformation stack:

 B57  → encoding layer
 H57  → full hash representation
 ID57 → compact identifier profile

Each layer serves a distinct purpose and MUST be used
according to its design constraints.

------------------------------------------------------------
15.1 B57 (ENCODING LAYER)
------------------------------------------------------------

B57 provides a bijective, entropy-preserving encoding
for raw binary data.

Typical use cases:

- binary-to-text conversion
- transport-safe encoding (URLs, filenames)
- human-readable representation of binary blobs
- QR encoding of arbitrary data
- copy/paste-safe tokens

Properties:

- preserves exact input data
- canonical representation
- avoids ambiguous characters

------------------------------------------------------------
15.2 H57 (HASH REPRESENTATION)
------------------------------------------------------------

H57 provides canonical representation of full cryptographic
hash outputs.

Typical use cases:

- file integrity verification
- content fingerprinting
- deduplication systems
- content-addressable storage
- Merkle trees and blockchain structures
- audit logs and tamper detection

Properties:

- preserves full hash entropy
- deterministic and canonical
- suitable for verification and comparison

------------------------------------------------------------
15.3 ID57 (IDENTIFIER PROFILE)
------------------------------------------------------------

ID57 provides compact, fixed-length identifiers derived
from cryptographic hashes.

Typical use cases:

- database primary keys (non-sequential)
- API identifiers
- distributed object IDs
- public resource identifiers
- logging and tracing references

Properties:

- deterministic
- canonical
- length-controlled
- human-readable

------------------------------------------------------------
15.4 SYSTEM-LEVEL USE (B57S STACK)
------------------------------------------------------------

B57S enables full pipeline composition:

 input → HASH → truncate → B57 → identifier

Typical system patterns:

1. Dual-layer identity:

   full_hash = H57(data)
   short_id  = ID57(data, ID57_LEN_128)

2. Storage vs exposure:

   store using H57
   expose ID57 externally

3. Deduplication:

   compare H57 for exact match
   index via ID57 for efficiency

------------------------------------------------------------
15.5 SECURITY-SENSITIVE VS NON-SENSITIVE USE
------------------------------------------------------------

Security-sensitive:

- MUST use ≥ ID57_LEN_128
- SHOULD use H57 when full entropy is required
- MUST use strong hash functions (e.g., BLAKE3)

Non-sensitive / UX-focused:

- MAY use shorter ID57 lengths
- MUST implement collision handling

------------------------------------------------------------
15.6 NON-GOALS
------------------------------------------------------------

B57S MUST NOT be used for:

- encryption
- reversible encoding of sensitive data
- authentication tokens
- random identifier generation

B57S does not replace cryptographic primitives.

------------------------------------------------------------
15.7 DESIGN SUMMARY
------------------------------------------------------------

Layer selection:

- B57  → exact binary representation
- H57  → full hash integrity
- ID57 → compact identifiers

============================================================
15.X ID57 SHORT IDENTIFIERS (ULTRA-COMPACT MODE)
============================================================

ID57 supports ultra-compact identifiers starting from
length 4 characters, optimized for human-centric usage.

Primary applications:

- short URLs
- QR codes
- user-visible IDs
- UI references
- temporary or scoped identifiers

Typical lengths:

- 4 chars → ~23-bit
- 5 chars → ~29-bit
- 6 chars → ~32-bit
- 8 chars → ~47-bit

------------------------------------------------------------
15.X.1 DESIGN INTENT
------------------------------------------------------------

Ultra-compact identifiers prioritize:

- minimal visual size
- fast manual entry
- low QR density
- usability in constrained environments

They are NOT designed for strong uniqueness guarantees.

------------------------------------------------------------
15.X.2 COLLISION CHARACTERISTICS
------------------------------------------------------------

Short identifiers have limited entropy and higher collision
probability.

Approximate practical limits:

- 4 chars (~23-bit) → small datasets (~thousands)
- 5 chars (~29-bit) → medium datasets (~tens of thousands)
- 8 chars (~47-bit) → larger datasets (~millions)

Values are approximate and depend on acceptable risk.

------------------------------------------------------------
15.X.3 REQUIRED SAFETY CONSTRAINTS
------------------------------------------------------------

Implementations using ultra-compact IDs MUST:

- perform collision detection
- support regeneration on collision
- scope identifiers within a namespace
- avoid global uniqueness assumptions
- treat identifiers as non-secure

------------------------------------------------------------
15.X.4 RECOMMENDED PATTERNS
------------------------------------------------------------

Pattern 1: Short + Full Mapping

 short_id = ID57(x, ID57_LEN_23)
 full_id  = H57(x)

- short_id used externally
- full_id used internally

------------------------------------------------------------

Pattern 2: Namespaced IDs

 short_id = ID57(namespace || x, ID57_LEN_23)

- reduces collision domain
- enables contextual uniqueness

------------------------------------------------------------

Pattern 3: Collision-Aware Allocation

 loop:
   id = ID57(x || counter, ID57_LEN_23)
   if not exists(id):
     store(id)
     break

------------------------------------------------------------
15.X.5 QR CODE USAGE
------------------------------------------------------------

ID57 short identifiers are well-suited for QR encoding:

- fewer characters → smaller QR size
- faster scanning
- better readability

Recommended:

- 4–8 chars → temporary / offline use
- ≥12 chars → persistent identifiers

------------------------------------------------------------
15.X.6 PROHIBITED USAGE
------------------------------------------------------------

Ultra-compact ID57 MUST NOT be used for:

- authentication
- authorization
- security tokens
- globally unique identifiers
- cryptographic identity

------------------------------------------------------------
15.X.7 ESCALATION RULE
------------------------------------------------------------

Systems MUST increase length when:

- dataset grows
- collision rate increases
- identifiers become cross-system

Recommended progression:

 4 → 8 → 12 → 16 → 22 chars

------------------------------------------------------------
15.X.8 DESIGN SUMMARY
------------------------------------------------------------

Ultra-compact ID57 identifiers are:

- human-optimized
- space-efficient
- collision-prone by design

They MUST be treated as:

- convenience identifiers
- scoped identifiers
- not security primitives
